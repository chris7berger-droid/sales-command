### Critical

- **B11** — **`team_members` write policies still allow tenant self-elevation (seed unfixed)**
  - `sql/rls_identity_tables.sql:64`
  - Evidence:
    ```
    CREATE POLICY "team_members_update" ON public.team_members
      FOR UPDATE TO authenticated
      USING  (tenant_id = public.get_user_tenant_id())
      WITH CHECK (tenant_id = public.get_user_tenant_id());
    ```
  - Commit `37fa00f` ("Closes S12: team_members self-elevation lockdown deployed") only touched `docs/BACKLOG.md` (1 file, 1 insertion — verified via `git show --stat`). The prod fix landed in `command-suite-db` migration `20260722120000_team_members_role_lockdown.sql`; the seed in **this** repo was NOT updated. `grep -r is_admin_or_manager sql/` returns zero matches. Any authenticated tenant member seeded from this file can UPDATE any team_members row in their tenant, including their own `role` — Sales → Admin/Manager in one PostgREST call. This unlocks every downstream role-gated policy (tenant_config, invoice deletes, manager dashboards). Fourth consecutive audit cycle unfixed in-repo; prod is fixed but the repo/seed divergence is itself a landmine — any fresh deploy or seed re-run re-introduces the vulnerability.
  - Spec: `CLAUDE_RLS.md` role-gating convention, OWASP A01, OWASP-ASVS V8.2.
  - Fix: add `AND public.is_admin_or_manager()` to USING and WITH CHECK on `team_members_insert/_update/_delete` in this seed to mirror the `command-suite-db` migration. Or delete the vulnerable policies from this seed and depend solely on the canonical migration.

### High

- **A4** — **`invite-user` logs full magic-link `action_link` via the `linkData` object**
  - `supabase/functions/invite-user/index.ts:128`
  - Evidence: `console.log("generateLink result:", { linkData, linkErr: linkErr?.message });`

- **B10** — **`tenant_config_update` lacks `is_admin_or_manager()` gate**
  - `sql/rls_identity_tables.sql:94`
  - Evidence:
    ```
    CREATE POLICY "tenant_config_update" ON public.tenant_config
      FOR UPDATE TO authenticated
      USING  (id = public.get_user_tenant_id())
    ```

- **B13** — **`proposal_signatures` DELETE policy permits audit-trail destruction by any tenant member**
  - `sql/rls_child_tables.sql:261`
  - Evidence:
    ```
    CREATE POLICY "proposal_signatures_delete" ON public.proposal_signatures
      FOR DELETE TO authenticated
      USING (tenant_id = public.get_user_tenant_id());
    ```
  - Any authenticated tenant member can DELETE any signature row — including signatures already recorded from real customer signings. Wipes legal/forensic record (signer_name, signer_email, signed_at, ip_address, pdf_url) while leaving the proposal in Sold. Non-repudiation broken. Carry-over.
  - Spec: OWASP-ASVS V7.1 (audit log integrity), OWASP A09.
  - Fix: signatures should be append-only. Drop the DELETE policy outright, or gate with `AND public.is_admin_or_manager() AND signed_at IS NULL`.

- **B-history-locker-anon-grant** — **`history_locker_phase1.sql` grants ALL to anon on the archive schema + default privileges landmine** (NEW)
  - `sql/history_locker_phase1.sql:119`
  - Evidence:
    ```
    GRANT USAGE ON SCHEMA archive TO anon, authenticated;
    GRANT ALL ON ALL TABLES IN SCHEMA archive TO anon, authenticated;
    GRANT ALL ON ALL SEQUENCES IN SCHEMA archive TO anon, authenticated;
    ALTER DEFAULT PRIVILEGES IN SCHEMA archive GRANT ALL ON TABLES TO anon, authenticated;
    ```
  - The archive schema (import_batches, legacy_records — imported customer/job history including contact info, addresses, dollars, raw_data jsonb) has ALL DML granted to anon. RLS with tenant-scoped policies filters live SELECTs today, BUT: (1) sequences do NOT respect RLS — `nextval('archive.import_batches_id_seq')` is callable by anon and can consume IDs. (2) `ALTER DEFAULT PRIVILEGES` means any FUTURE archive table gets `ALL TO anon` by default; a maintainer who forgets `ENABLE ROW LEVEL SECURITY` on a new archive table creates instant anon full-read of imported history. Least-privilege violated as a persistent landmine.
  - Spec: least privilege, `CLAUDE_RLS.md`, OWASP-ASVS V1.4.1.
  - Fix: replace with `GRANT SELECT, INSERT, DELETE ON archive.import_batches, archive.legacy_records TO authenticated;` (no anon, no ALL, no ALL SEQUENCES). Drop the `ALTER DEFAULT PRIVILEGES … TO anon` lines. If anon truly needs archive access, add explicit per-table grants next to their RLS policies.

- **D2** — **`PublicInvoicePage` joins `proposal_wtc(*)` — leaks burden_rate, markup_pct, materials cost basis to anon**
  - `src/pages/PublicInvoicePage.jsx:51`
  - Evidence: `.from("invoice_lines").select("*, proposal_wtc(*, work_types(name))").eq("invoice_id", inv.id);`
  - `proposal_wtc` columns include burden_rate, ot_burden_rate, tax_rate, regular_hours, ot_hours, markup_pct, materials (jsonb with unit costs), sub_areas, travel, discount, sales_sow. Every customer viewing an invoice sees the full internal cost basis + margin in their Network tab. D1 (invoices select(\*)) was fixed via explicit column list + column-level REVOKE/GRANT, but D2's sibling `proposal_wtc` leak was left open. Carry-over since 2026-06-01.
  - Spec: `CLAUDE.md`, `CLAUDE_RLS.md`, OWASP-ASVS V5.1.3, OWASP A01.
  - Fix: narrow to `proposal_wtc(id, work_types(name), locked_line_total)`; use the server-computed locked total instead of running `calcWtcPrice` client-side. Follow with `REVOKE SELECT ON public.proposal_wtc FROM anon; GRANT SELECT (id, work_type_id, locked_line_total) TO anon;`.

### Medium

- **B-db_hardening-stale-tenant-fn** — **`db_hardening_phase1.sql` defines `get_user_tenant_id()` as `SELECT id FROM tenant_config LIMIT 1` — cross-tenant landmine on re-run** (NEW)
  - `sql/db_hardening_phase1.sql:12`
  - Evidence:
    ```
    CREATE OR REPLACE FUNCTION public.get_user_tenant_id()
    RETURNS uuid AS $$
      SELECT id FROM public.tenant_config LIMIT 1;
    $$ LANGUAGE sql SECURITY DEFINER STABLE;
    ```
  - Pre-hardening body that migration `20260509120000` removed in prod. Overwritten by the auth-aware body in `rls_identity_tables.sql:129` / `rls_cleanup_and_remaining.sql:377` when seeds run in order — but if an operator re-runs `db_hardening_phase1.sql` in isolation (e.g. to reset an index), the function silently reverts to returning the first tenant for EVERY caller. Every RLS policy on every table then evaluates true for everyone; single-tenant assumptions become cross-tenant reads/writes on any second tenant provisioned. Also lacks `SET search_path = public` (trojan-search-path risk under SECURITY DEFINER).
  - Spec: `CLAUDE_RLS.md` tenant isolation, OWASP-ASVS V5.1.1 (search-path fixation).
  - Fix: replace with the auth-aware body used in `rls_identity_tables.sql:129` (`SELECT tenant_id FROM team_members WHERE auth_id = auth.uid() AND active LIMIT 1`, with `SET search_path = public`); or delete the definition here and depend on the canonical file.

- **B-viewing-token-echo** — **`PublicInvoicePage` echoes back its own `viewing_token` in the SELECT list** (NEW)

Caller already presented it in `x-viewing-token`, but the token is now embedded in a JSON response that browser history, disk cache, transport-layer captures, or DOM-inspecting extensions can reuse (per prior audits, viewing tokens don't rotate). Minor best-practice violation of not echoing bearer tokens back to their holder.
  - Spec: OWASP-ASVS V3.5.3.
  - Fix: drop `viewing_token` from the SELECT list — the page doesn't use it after the fetch (verified).
