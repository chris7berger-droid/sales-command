### High

- **A1** — **Hardcoded prod Supabase URL fallback in public client** (carry-over)
  - `src/lib/supabasePublic.js:16`
  - Evidence: `const SUPABASE_URL = import.meta.env.VITE_SUPABASE_URL || "https://pbgvgjjuhnpsumnowuym.supabase.co";`
  - Any staging/preview build shipped without `VITE_SUPABASE_URL` silently hits production. Every public signing/viewing page (which uses `createPublicClient`) inherits the fallback, defeating env-driven environment separation and hiding misconfigurations.
  - Spec: OWASP-ASVS V14.2.1, OWASP A05.
  - Fix: drop the `||` fallback; throw at module load if `VITE_SUPABASE_URL` is unset, matching `src/lib/supabase.js:8`.

- **A2** — **Hardcoded publishable anon key fallback in public client** (carry-over)
  - `src/lib/supabasePublic.js:20`
  - Evidence: `const SUPABASE_KEY = import.meta.env.VITE_SUPABASE_ANON_KEY || "sb_publishable_LL6wYC7kJDPQfGYeKAaLaWKoK";`
  - A prod anon key is baked into source so every commit/checkout redistributes it; rotation becomes a code push. A misbuilt bundle still authenticates against prod. Carry-over.
  - Spec: OWASP-ASVS V2.10.4, OWASP A05.
  - Fix: remove the string fallback; require `VITE_SUPABASE_ANON_KEY` via env and fail loudly if missing.

- **A1b** — **Hardcoded prod Supabase URL fallback in Login reset flow** (carry-over)
  - `src/pages/Login.jsx:59`
  - Evidence: `` `${import.meta.env.VITE_SUPABASE_URL || "https://pbgvgjjuhnpsumnowuym.supabase.co"}/functions/v1/reset-password` ``
  - Second hardcoded prod URL, in the password-reset fetch path — same env-separation risk as A1. A staging/misbuilt Login page POSTs to prod's reset-password endpoint. Carry-over.
  - Spec: OWASP-ASVS V14.2.1, OWASP A05.
  - Fix: route through the central client / a validated env constant; drop the string fallback.

- **A2b** — **Hardcoded publishable anon key fallback in Login reset flow (DIFFERENT literal from A2)** (carry-over)
  - `src/pages/Login.jsx:62`
  - Evidence: `apikey: import.meta.env.VITE_SUPABASE_ANON_KEY || "sb_publishable_v7XktVvkAlX7y5f6xoFjng_AaLaWKoK"`
  - A different literal from A2 — two distinct hardcoded publishable keys live in the tree, so rotating one still leaves the other. Carry-over.
  - Spec: OWASP-ASVS V2.10.4, OWASP A05.
  - Fix: remove the string fallback; use the same env-driven value the rest of the app reads.

- **A4** — **Magic-link auth token logged in `invite-user`** (carry-over — FOURTH cycle)
  - `supabase/functions/invite-user/index.ts:128`
  - Evidence: `console.log("generateLink result:", { linkData, linkErr: linkErr?.message });`
  - `linkData.properties.action_link` is a single-use magic-link credential that logs the recipient straight in. Anyone with edge-function log access (Supabase dashboard viewer, log-shipper sink, third-party observability integration) can hijack the invitee's session — worse than PII, this is a live credential in the logs. Fourth cycle unfixed.
  - Spec: OWASP-ASVS V7.1.1, OWASP A09, A07.
  - Fix: `console.log("generateLink result:", { hasLink: !!linkData?.properties?.action_link, linkErr: linkErr?.message });`

### Medium

- **A5** — **Recipient email address logged in `stripe-webhook` sendEmail** (carry-over)
  - `supabase/functions/stripe-webhook/index.ts:49`
  - Evidence: `console.log("Email to", to, ":", res.status);`
  - Customer email addresses (payment receipts) are logged on every send; log-store retention effectively becomes indefinite PII retention outside the primary DB and its RLS.
  - Spec: OWASP-ASVS V7.1.3, OWASP A09, GDPR data-minimization.
  - Fix: `console.log("Email send status:", res.status);` — drop `to`.

- **A6** — **Invitee + inviter emails and names logged in `invite-user`** (carry-over)
  - `supabase/functions/invite-user/index.ts:88`
  - Evidence: `console.log("invite-user invoked", { email, name, teamMemberId, senderEmail, senderName });`
  - Every invite writes four PII fields to plain edge logs. Same log-retention concern as A5.
  - Spec: OWASP-ASVS V7.1.3, OWASP A09.
  - Fix: log only `teamMemberId` + a hashed email; drop names and sender identity.

- **A7** — **Recipient + rep emails logged in `send-proposal`** (carry-over)
  - `supabase/functions/send-proposal/index.ts:139`
  - Evidence: `console.log("send-proposal invoked", { proposalId, recipientEmail, repEmail, proposalNumber });`
  - Customer recipient and internal rep email land in the log on every proposal send.
  - Spec: OWASP-ASVS V7.1.3, OWASP A09.
  - Fix: log `proposalId` + `proposalNumber` only; drop `recipientEmail`/`repEmail`.

- **A8** — **Recipient email logged in `send-pay-app` invocation** (NEW)
  - `supabase/functions/send-pay-app/index.ts:99`
  - Evidence: `console.log("send-pay-app invoked", { payAppId, invoiceId, recipientEmail });`
  - Same shape as A5/A7: customer email is written to plain edge logs on every pay-app send. PII exposure in logs.
  - Spec: OWASP-ASVS V7.1.3, OWASP A09.
  - Fix: log `payAppId` + `invoiceId` only; drop or hash `recipientEmail`.

- **A9** — **Recipient email logged by shared `repNotify.sendEmail`** (NEW)
  - `supabase/functions/_shared/repNotify.ts:118` (also `:115` rejection + `:121` throw)
  - Evidence: `console.log(\`${tag}: emailed ${to} — ${body}\`);`
  - Shared helper used by `proposal-approved` and `follow-up-reminders` logs the rep's raw email address on every successful send (and again on rejection + throw). Every new edge function using this helper inherits the leak.
  - Spec: OWASP-ASVS V7.1.3, OWASP A09.
  - Fix: redact `to` (mask local-part) in all three sites; keep tag + status + body-slice for observability.

### Low

- **A10** — **Full Resend response body logged verbatim in `reset-password`** (NEW)
  - `supabase/functions/reset-password/index.ts:129`
  - Evidence: `console.log("Reset email response:", emailRes.status, emailResBody);`
  - Full Resend response body written to logs on every reset. Resend responses carry the message id and can echo the recipient in error payloads; defense-in-depth minimization issue.
  - Spec: OWASP-ASVS V7.1.3, OWASP A09.
  - Fix: log only `emailRes.status` (and `emailRes.ok`) — parse the body for an id if needed and log that alone.

- **A11** — **Resend response body slice logged in `send-invoice` main path** (NEW)
  - `supabase/functions/send-invoice/index.ts:465`
  - Evidence: `console.log("Main email response:", mainRes.ok, mainRes.txt.slice(0, 200));`
  - First 200 bytes of the Resend body land in logs on every main-recipient invoice send. Provider errors sometimes echo the recipient into the body.
  - Spec: OWASP-ASVS V7.1.3, OWASP A09.
  - Fix: log `mainRes.ok` + status only; drop the body slice or gate it behind a debug-mode env flag.
