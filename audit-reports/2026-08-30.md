### High

- **B-archive-grant-anon** — **`archive` schema `GRANT ALL … TO anon` with `ALTER DEFAULT PRIVILEGES`** (carry-over)
  - `sql/history_locker_phase1.sql:118-122`
  - Evidence: `GRANT USAGE ON SCHEMA archive TO anon, authenticated; GRANT ALL ON ALL TABLES IN SCHEMA archive TO anon, authenticated; ALTER DEFAULT PRIVILEGES IN SCHEMA archive GRANT ALL ON TABLES TO anon, authenticated;`
  - Anon is granted ALL DML on every current AND future archive table. Today RLS + `archive.get_user_tenant_id()` returning NULL for anon deny reads, but the grants remain the only backstop. Any future `archive.*` table added without `ENABLE ROW LEVEL SECURITY` (e.g. a helper/staging table) ships wide open — direct 2026-04-26 class exposure. There is no legitimate anon use case for the archive schema.
  - Spec: `CLAUDE_RLS.md`, OWASP-ASVS V8.2.1, OWASP A01.
  - Fix: `REVOKE ALL ON ALL TABLES/SEQUENCES IN SCHEMA archive FROM anon; ALTER DEFAULT PRIVILEGES IN SCHEMA archive REVOKE ALL ON TABLES/SEQUENCES FROM anon;` keep only authenticated grants.

- **B-proposal_wtc-anon-select** — **Anon signing/viewing tokens expose `proposal_wtc` cost basis via direct PostgREST query** (RE-SCOPED from B-PublicInvoicePage-wide-select)
  - `src/pages/PublicInvoicePage.jsx:60-67` (in-file acknowledgement); policy body lives in `command-suite-db` migration `20260427180000_add_token_gated_policies.sql`
  - Evidence: `// BUT THIS ALLOW-LIST IS NOT THE SECURITY BOUNDARY — corrected 2026-08-10 by security review. proposal_wtc carries a TABLE-level anon SELECT grant, so a link holder can query burden_rate / markup_pct / pw_rate / materials / discount straight from PostgREST regardless of what this page selects.`
  - The prior wide-select at `:51` was resolved (now explicit column allow-list at `:73-79`), which keeps cost basis out of the DOM — but the underlying anon SELECT policy on `proposal_wtc` (via `x-signing-token` / `x-viewing-token` match) still returns every column. Anyone the signing or viewing link is shared with (customer, forwarded email recipient) can hit `/rest/v1/proposal_wtc?select=*` with the publishable anon key + the token header and read `burden_rate`, `ot_burden_rate`, `markup_pct`, `pw_rate`, `materials`, `discount`. Explicitly acknowledged as unfixed (backlog S13). Fourth audit cycle — the DOM mitigation ships but the DB fix is still in command-suite-db.
  - Spec: `CLAUDE_RLS.md`, OWASP-ASVS V8.3.4, OWASP A01.
  - Fix: in `command-suite-db`, replace `proposal_wtc`'s anon SELECT policy with a column-restricted view (or `REVOKE SELECT ON burden_rate, ot_burden_rate, pw_rate, pw_ot_rate, markup_pct, materials, discount FROM anon`); the public pages already read `locked_line_total` snapshots and don't need cost inputs.

- **B11 (legacy-seed)** — **`team_members_update` policy is UNGATED — role-escalation + account-takeover primitive within tenant** (carry-over)
  - `sql/rls_identity_tables.sql:64`
  - Evidence: `CREATE POLICY "team_members_update" ON public.team_members FOR UPDATE TO authenticated USING (tenant_id = public.get_user_tenant_id()) WITH CHECK (tenant_id = public.get_user_tenant_id());`
  - Any authenticated user in a tenant can UPDATE every row of `team_members`. Because `get_user_tenant_id()` reads `team_members WHERE auth_id = auth.uid() AND active = true`, an ordinary rep can rewrite their own `role` to Admin/Manager, flip a colleague's `active` flag, or set `auth_id` on a colleague's row to their own `auth.uid()` — full role-escalation + takeover. Prod state claimed fixed via `command-suite-db` migration `20260722120000_team_members_role_lockdown.sql` (§8 smoke-verified 2026-07-22, unverifiable from this repo). Legacy seed remains a landing hazard on a fresh deploy.
  - Spec: OWASP-ASVS V4.1.3, OWASP A01.
  - Fix: split into a self-update policy (`auth_id = auth.uid()` with `WITH CHECK` on role/active/tenant_id/auth_id unchanged) + admin-only policy gated on `is_admin(auth.uid())`; or delete this seed file with a comment pointing at the command-suite-db migration.

- **B10 (legacy-seed)** — **`tenant_config_update` lets any authenticated tenant user rewrite billing goals, Stripe IDs, defaults** (carry-over)
  - `sql/rls_identity_tables.sql:94`
  - Evidence: `CREATE POLICY "tenant_config_update" ON public.tenant_config FOR UPDATE TO authenticated USING (id = public.get_user_tenant_id()) WITH CHECK (id = public.get_user_tenant_id());`
  - Any authenticated tenant user (rep or otherwise) can UPDATE every column of their tenant_config — `company_name`, `monthly/yearly_billing_goal`, `default_burden_rate`, `default_tax_rate`, `stripe_customer_id`, `stripe_subscription_id`, `subscription_status`, `apps[]`, `logo_url`, `license_number`. Pairs with D3.
  - Spec: OWASP-ASVS V4.1.3, OWASP A01.
  - Fix: same lockdown pattern as B11 — add `USING is_admin(auth.uid())` or route sensitive writes through a SECURITY DEFINER RPC.

- **B13 (legacy-seed)** — **`proposal_signatures_delete` allows any tenant user to destroy signed proposal evidence** (carry-over)
  - `sql/rls_child_tables.sql:261`
  - Evidence: `CREATE POLICY "proposal_signatures_delete" ON public.proposal_signatures FOR DELETE TO authenticated USING (tenant_id = public.get_user_tenant_id());`
  - Any authenticated tenant user can DELETE the signature record for any proposal in their tenant. `proposal_signatures` is the legal-binding electronic-signature audit trail (`signer_name`, `signed_at`, `ip_address`, `pdf_url`); deleting is repudiation-friendly + irreversible. Pull-back today already exercises this DELETE path via ProposalDetail.handlePullBack (D-ProposalDetail-batch).
  - Spec: OWASP-ASVS V7.3.1, OWASP A08, A09.
  - Fix: drop the DELETE policy (append-only signatures) or restrict `USING is_admin(auth.uid())`; if pull-back needs to void, add a `voided_at` column instead of DELETE.

- **B-legacy-search-path** — **`sql/db_hardening_phase1.sql:12` `get_user_tenant_id()` seed body has no `SET search_path` AND uses `tenant_config` fallback** (carry-over)
  - `sql/db_hardening_phase1.sql:12`
  - Evidence: `CREATE OR REPLACE FUNCTION public.get_user_tenant_id() RETURNS uuid AS $$ SELECT id FROM public.tenant_config LIMIT 1; $$ LANGUAGE sql SECURITY DEFINER STABLE;`
  - Earliest SECURITY DEFINER body has no `SET search_path` and returns the first tenant regardless of caller. Overwritten by the hardened version in `rls_identity_tables.sql:129-137` and `rls_cleanup_and_remaining.sql:377`, but between the two runs (or if the second file is skipped) the function is exposed to search_path injection AND collapses tenant isolation to 'first tenant wins'.
  - Spec: OWASP-ASVS V5.3.5, OWASP A08 — Supabase function search_path hardening.
  - Fix: replace the body with the auth-aware version + `SET search_path = public`; also add `SET search_path` to `set_updated_at()` and `fn_auto_in_progress()` in the same file.

- **B-soft-delete-select** — **SELECT policies on `proposals`/`invoices` don't filter `deleted_at IS NULL`** (NEW)
  - `sql/rls_core_tables.sql:138` (proposals), `:185` (invoices)
  - Evidence: `CREATE POLICY "proposals_select" ON public.proposals FOR SELECT TO authenticated USING (tenant_id = public.get_user_tenant_id());`
  - `proposals` and `invoices` both carry a `deleted_at` soft-delete column, but the SELECT policies don't add `AND deleted_at IS NULL`. Every list/detail query in the app must remember to filter — one missed spot and a soft-deleted row becomes visible again. Defense-in-depth only (same tenant), not a confidentiality leak.
  - Spec: OWASP-ASVS V8.3.4, OWASP A04.
  - Fix: add `AND deleted_at IS NULL` to the SELECT USING clause on `proposals` and `invoices`; expose an explicit view / RPC for trash-recovery UI admins can query.
