### High

- **B-archive-grant-anon** — **`archive` schema `GRANT ALL … TO anon` with `ALTER DEFAULT PRIVILEGES`** (carry-over)
  - `sql/history_locker_phase1.sql:118`
  - Evidence: `GRANT ALL ON ALL TABLES IN SCHEMA archive TO anon, authenticated; GRANT ALL ON ALL SEQUENCES IN SCHEMA archive TO anon, authenticated; ALTER DEFAULT PRIVILEGES IN SCHEMA archive GRANT ALL ON TABLES TO anon, authenticated;`
  - `GRANT ALL` includes TRUNCATE, which bypasses RLS entirely. Anon holds full DML on `archive.import_batches` + `archive.legacy_records`, and `ALTER DEFAULT PRIVILEGES` keeps re-granting on every future archive table. Data protection today rests on `archive.get_user_tenant_id()` returning NULL for anon → RLS denies. Two defense-in-depth failures: (a) `TO authenticated` not specified on policies (defaults to PUBLIC), (b) UPDATE not covered by RLS while grant includes UPDATE. Any future permissive policy — or a SECURITY INVOKER RPC issuing TRUNCATE — nukes every tenant's history. Legacy seed; a fresh deploy re-establishes the grants.
  - Spec: `CLAUDE_RLS.md` (least privilege), OWASP-ASVS V8.1.5, OWASP A05.
  - Fix: `GRANT SELECT, INSERT, DELETE ... TO authenticated` only (never anon, never ALL); scope every RLS policy with `TO authenticated`; `ALTER DEFAULT PRIVILEGES ... TO authenticated` only.

- **B11 (legacy-seed)** — **`sql/rls_identity_tables.sql:64` ships the pre-lockdown `team_members_update` policy** (carry-over)
  - `sql/rls_identity_tables.sql:64`
  - Evidence: `CREATE POLICY "team_members_update" ON public.team_members FOR UPDATE TO authenticated USING (tenant_id = public.get_user_tenant_id()) WITH CHECK (tenant_id = public.get_user_tenant_id());`
  - Any authenticated tenant user can UPDATE any team_members row — elevate self to Admin, flip active flags, or rewrite another user's auth_id to hijack identity. Prior CRITICAL. **Prod claim**: `command-suite-db` migration `20260722120000_team_members_role_lockdown.sql` deployed 2026-07-22 with §8 smoke-verified; CANNOT verify prod from this repo. However, this legacy seed still contains the anti-pattern — a fresh deploy re-introduces the vulnerability, and the file is not marked deprecated.
  - Spec: `CLAUDE_RLS.md` role-gating, OWASP-ASVS V8.2, OWASP A01.
  - Fix: split into (a) self-update with column-list excluding role/active/tenant_id/auth_id; (b) admin-update gated on `EXISTS(SELECT 1 FROM team_members WHERE auth_id = auth.uid() AND role = 'Admin' AND active = true)`. Or delete this seed file with a comment pointing at the command-suite-db migration.

- **A4** — **`invite-user` logs full magic-link `action_link` via the `linkData` object** (carry-over)
  - `supabase/functions/invite-user/index.ts:128`
  - Evidence: `console.log("generateLink result:", { linkData, linkErr: linkErr?.message });`

- **B-proposals-invoices-select-deleted-at** — **`proposals_select` + `invoices_select` RLS policies don't filter `deleted_at IS NULL` / `voided_at IS NULL`** (NEW)
  - `sql/rls_core_tables.sql:138` (proposals), `:185` (invoices)
  - Evidence: `CREATE POLICY "proposals_select" ON public.proposals FOR SELECT TO authenticated USING (tenant_id = public.get_user_tenant_id());` — no `deleted_at IS NULL`. Same shape at invoices_select:185.

  - Spec: `CLAUDE.md` Data Integrity, OWASP A04.
  - Fix: add `AND deleted_at IS NULL` to proposals_select USING; `AND deleted_at IS NULL AND voided_at IS NULL` to invoices_select USING. Add a separate admin-scoped policy or view (e.g., `proposals_trash`) for restore flows.

- **B-leads-intake-ratelimit** — **`leads-intake` accepts unlimited POSTs on shared-secret match; no per-IP throttle or per-tenant daily cap** (NEW)
  - `supabase/functions/leads-intake/index.ts:47`
