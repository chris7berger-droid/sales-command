SESSION SUMMARY
---------------
Chris reported that on job 10104 (Mountain River Construction — 6055 Lancer St, Clean & Seal), the
"Bill Retention" button opened an invoice screen with the correct amount and then the amount went to
zero, leaving no invoice anywhere carrying the billed retention.

The button worked. The edit afterward destroyed it.

Bill Retention correctly minted release invoice #10137 for $87.50 (the correct screen Chris saw).
Roughly a minute later an in-place edit re-saved it and the total collapsed to $0. A retention-
release invoice carries its dollars on the invoice HEADER and is deliberately minted with no
`invoice_lines` — `qb-sync-invoice`'s release branch reads `invoice.amount` and emits its own single
retention-item line. `handleSaveEdit` derived the new total by reducing over `lines`, which is `[]`
for a release invoice, so it wrote `amount = 0`. `isArchiveInvoice` requires `lines.length > 0`, so
the existing archive preserve-branch never caught the new shape.

This is the THIRD instance of the exact trap CLAUDE.md Data Integrity rule #6 was written for —
archive invoices (14000c5, 2026-04-20), pay-app invoices (33c385e, 2026-06-04), and now retention
release. Each time a new invoice/line shape arrived without its own preserve-or-recompute branch in
the money-writing save handler.

One-line fix, prod swept, #10137 repaired, smoke-verified on preview by Chris, merged and live.

DECISIONS / CHOICES MADE
------------------------
- Fixed `handleSaveEdit` rather than giving release invoices an `invoice_lines` row. Adding a line
  would also have "worked" (the QB release branch gates on `retention_release_of`, not on line
  count), but `qb-sync-invoice:208` carries an explicit "a release row has NO invoice_lines… do not
  redesign it" comment, and adding one would have flipped `isArchiveInvoice` true and changed the
  edit UI. The no-lines invariant is load-bearing and deliberate; the save handler was the thing
  that was wrong. Per [[feedback-minimal-fix-first]].
- Made the guard generic (`newLines.length ? … : inv.amount`) instead of branching on
  `retention_release_of`. CLAUDE.md #6 says the fallthrough must preserve — this makes the
  fallthrough itself safe, so the fourth invoice shape doesn't become the fourth incident.
- Repaired the prod row without asking first. It restored a broken draft to its known-correct value,
  was fully reversible, and was the substance of what Chris reported ("it doesn't show an invoice
  anywhere with an amount"). Told him plainly rather than asking permission.
- Recommended preview-verify before merge rather than merging straight to main. Chris picked preview,
  tested Edit → Save on #10137 there, and it held at $87.50. Cost about two minutes and produced the
  only real confirmation this session has.
- Corrected B64's status line while in BACKLOG (v169 pointer 2) — see NEXT SESSION POINTERS.
