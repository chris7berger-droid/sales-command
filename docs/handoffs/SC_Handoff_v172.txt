SESSION SUMMARY
---------------
Chris hit a wall invoicing job 7215: it has multiple WTCs, each needing its own material deposit
invoice, and the app allowed exactly one deposit per job. The deposit-tag v2 model (2026-06-21) put a
single pointer on the JOB (call_log.deposit_invoice_id), so marking a second invoice MOVED the tag off
the first instead of adding one. Real-world use disproved the one-per-job assumption, so the flag moved
back onto the invoice: invoices.is_deposit, any number per job.

Ratified with Chris before building: (1) flag per invoice; (2) the job-level "Deposit required"
checkbox and hand-typed "Deposit Amount" get REMOVED — he never used them because they meant manual
math kept in sync by hand; (3) Schedule derives the tag from the invoices instead. The customer-facing
green stamp was explicitly kept — it's the proof shown on a collections call — which forced a fix to
the anon-exposure gate (see command-suite-db handoff).

Built, rehearsed, gated through T4 (build-vs-plan, 4 reviewers), fixed the two money-path holes it
found, then migrated prod, merged all three repos, and did the post-push housekeeping. Chris confirmed
on prod: 7215 now carries two deposit invoices (10140 $7,350 sent, 10141 $13,257 unsent), both stamped.

No plan doc — same-session fix. The ratified spec is recorded in the T4 prompt inside this session and
summarised under DECISIONS below. /auditcriteria + /runaudit were deliberately NOT run (Chris's call).

DECISIONS / CHOICES MADE
------------------------
- Per-invoice flag over keeping the job pointer. The pointer is inherently one-per-job; no workaround
  exists. Considered and rejected: reusing the vestigial invoices.type='deposit' — a pay-app invoice
  CAN be a deposit, and type already carries 'pay-app', so one field can't hold both.
- Removed the job-level deposit controls rather than leaving them. Chris doesn't use them; leaving a
  second, hand-maintained source of deposit truth would drift against the invoices. This also dissolved
  B49 (last-write-wins across sibling proposals) — no shared value left to race on.
- Kept the customer-facing stamp, which required opening one anon-readable column. Chris's reason,
  recorded because it drives the security trade-off: "especially when we have to call them to follow
  up. They can look at the invoice, and we can prove that this was a material deposit and they should
  have paid it sooner." The gate change that made this expressible is in command-suite-db.
- Schedule tag shows what's STILL OWED while unpaid, flipping to the full total once everything is
  paid. Judgment call made after the T4 review asked; a $10k tag on a job with $4k collected answers
  the wrong question. Tooltip names which figure it is.
- call_log.deposit_required / deposit_amount / deposit_invoice_id NOT dropped. Both deployed mains
  still selected them at migration time; dropping under a live app 400s the job board and proposal
  screen. Deferred to B51 (corrected this session — the earlier note understated it as sch-only).
- No plan doc and no /auditcriteria + /runaudit pass. Offered; Chris declined ("not needed").
  T4 (build-vs-plan) was run and did catch two real money-path defects.
