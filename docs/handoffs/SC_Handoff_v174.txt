SESSION SUMMARY
---------------
Chris opened salescommand.app/settings, saw the Work Types list carrying rows tagged DEFAULT next to
the CUSTOM ones, and asked to remove them: "Those are all redundant, and they do not have SOWs."

Diagnosis: Settings loaded ALL 84 `work_types` rows. 51 are seeded system rows (`tenant_id IS NULL`);
33 are tenant-owned. System rows can't hold a SOW, which is why they rendered "Add SOW" instead of
Edit/Delete. The premise was half right — they ARE the redundancy source, but they are NOT all
redundant (see OPEN ITEM). Reps picking a SOW-less default is how the near-duplicate names got
created in the first place: "Clean and Seal" vs "Clean & Seal", "Joint fill" vs "Joint Fill Caulking",
"Flattening" vs "Flatten", "Shot Blast" vs "Shot Blasting", "Patching" vs "Heavy Patching".

Chris ratified the shape explicitly: leave the rows in the DATABASE, remove them from the UI. Nothing
is deleted anywhere in this session's code — historical jobs, proposals and WTCs keep resolving their
work-type names exactly as before.


CHANGES SHIPPED (sales-command)
-------------------------------
NEW FILE — src/lib/workTypes.js — the rule lives in ONE place so it can't drift:

    selectableWorkTypes(all, keepIds = [])
      → keeps a row if: it's in keepIds, OR (tenant_id set AND active !== false)
      → sorted by name

  keepIds is the escape hatch and the reason this is safe: anything already tagged on the record being
  edited stays in the list. Without it, opening an old job tagged with a now-hidden work type would
  show that box unchecked, and saving would silently drop the tag. Filter bars deliberately do NOT use
  this helper — they need the full catalog to filter historical records.

Why TEST couldn't just be deleted: `proposal_wtc_work_type_id_fkey` is NO ACTION and three
proposal_wtc rows still point at work type 89 — all on proposals soft-deleted on 2026-04-13 (x2) and

they keep holding the FK. Chris was offered a cleanup of those 3 rows and declined: "no, that's my
problem... go ahead and hide that one too." Hence the retire path rather than a delete.


DECISIONS
---------
1. Hide, don't delete. Rows stay in the DB; only selectability changes. Chris's call, stated twice.
2. Already-tagged records keep showing their work type (keepIds), so no re-tag pass was needed before
   shipping and no save can silently drop a tag.
3. Filter bars keep the full catalog — hiding defaults there would make old jobs unfilterable.
4. Retire reuses the existing `active` column rather than adding a schema concept. No migration.
5. There is no Hide/Unhide button in the UI yet — retiring another work type today means one SQL
   flip. Not built because only TEST needed it; worth a button if it happens again.
