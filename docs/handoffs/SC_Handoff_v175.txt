Chris: "The follow-up needs to send an email to the sales person in charge of the job, and
sales is also not getting any notification. Once a proposal is approved, they need to get an
email notifying them."

Three separate holes, one symptom — reps were never told their work landed.

1. FOLLOW-UP REMINDERS NEVER EXISTED. `call_log.follow_up` has been written since day one and
   the New Inquiry wizard has always read "A 30-day reminder will be sent to the sales rep if
   this job's status hasn't changed." Nothing anywhere read that column except the Call Log
   list's overdue colouring. No cron, no function, no email. The on-screen promise was fiction.

2. INTERNAL APPROVE EMAILED NOBODY. `ProposalDetail.handleInternalApprove` flipped status,
   stamped approved_by/approval_reason, and kicked qb-create-job — with no email on the path.
   Only a customer e-signature had any email at all. Prod check: 21 of the last 25 approvals
   went through Internal Approve, so nearly every sold job notified no one.

3. THE E-SIGN PATH DIDN'T DELIVER EITHER — and this one was the real lesson. See DECISIONS.

Incidental find (fixed): the nightly orphan-user security alarm had failed on EVERY run since
2026-06-09 with `unrecognized configuration parameter "app.settings.supabase_url"`. It had
never once run successfully.

DECISIONS
---------
D1. THE APPROVAL NOTIFICATION LIVES IN THE DATABASE, NOT THE APP. This is the important one.
    First cut invoked an edge function from the browser. Then prod logs for a live customer
    signature at 23:04:47 showed what actually happens:
        .865  browser sends the CORS preflight for proposal-signed
        .896  browser calls the mark_proposal_signed RPC DIRECTLY instead
        .930  proposal Sold, "Proposal Accepted" on screen
              the function's POST never happens at all
    PublicSigningPage has a fallback that commits the signature itself whenever the edge call
    doesn't land. That fallback is CORRECT — the customer must always be able to sign — but it
    means the edge function is not a reliable place for anything that must happen. No amount of
    hardening inside the function fixes it; the function isn't running. So the notifier moved to
    a trigger on `proposals.status`, the one thing every approval route has in common.
    Saved to memory as `project_signing_page_silent_fallback`.

D2. TRIGGER FIRES ONLY ON A TRANSITION INTO Sold/Signed, and skips `is_archive_proposal`.
    Archive imports insert historical closed-out work straight to Sold — records, not news.
    Re-saving an already-Sold row does not re-notify; pull-back → re-approve does.

D3. EXACTLY ONE NOTIFIER. proposal-signed and Internal Approve both stopped sending their own
    mail when the trigger landed, so there is no double-send path.

D4. THE 77 ALREADY-OVERDUE FOLLOW-UPS STAY SUPPRESSED — SETTLED, DO NOT RE-OPEN.
    Firing on day one would have sent John Paul a 49-row email and Joe a 28-row email, oldest
    dated 2026-04-13. Chris was offered the release, took it, saw the counts, and reversed:
    "I don't want these guys getting an email with 49 things and 28 things to go check through.
    It just needs to work from here forward." Released and re-suppressed same session; verified
    0 rows would email.
    The old dates remain on the jobs and still show red on the Call Log list — nothing deleted,
    they just don't generate mail. Editing one of those jobs to a NEW follow-up date re-arms it
    normally; only the stale values are muted.
    If a future session ever needs the opposite, it is one statement (also in the migration
    header) — but treat it as a decision to re-litigate with Chris, not a cleanup task:
        UPDATE public.call_log SET follow_up_reminded_for = NULL
         WHERE stage NOT IN ('Sold','Lost') AND follow_up IS NOT NULL;

D5. follow_up_reminded_for STORES WHICH DATE WAS REMINDED, not when mail was last sent. That
    makes the job idempotent, catch-up capable (a missed night isn't a lost reminder), and
    re-armable (push a date out and it fires again on the new one).

D6. ORPHAN ALARM REPAIRED BY DROPPING THE GUC DEPENDENCY, not by provisioning the GUCs — they
    need superuser and cannot be set on this managed project (the same block 20260609120100
    documented). URL is now literal, service-role header dropped, function redeployed
    --no-verify-jwt. 20260609120100 already recorded that the platform JWT gate "admits ANY
    authenticated tenant user", so x-cron-secret was always the real gate; now it's the only one.

D7. BOTH MIGRATIONS GUARD ON pg_cron / pg_net PRESENCE. Not defensive padding — an unguarded
    `cron.job` reference makes a migration unrehearsable, which would mean pushing to the shared
    DB having never once executed the file. The guard RAISEs a NOTICE, so a prod run that somehow
    found no extension is visible in the push output rather than silently scheduling nothing.
