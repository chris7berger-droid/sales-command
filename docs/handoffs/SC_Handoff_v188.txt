CHANGES SHIPPED (src/pages/Invoices.jsx + docs/BACKLOG.md)
═══════════════════════════════════════════════════════════════════════════════
ROOT CAUSE: handleVoidConfirm's synced pull-back ran a TWO-ROW void+replacement —
  voided #567 in QB (operation=void, keeps qb_invoice_id + DocNumber), marked the
  SC row voided_at, and INSERTED a new invoice at the next free id as the
  correction. So the corrected invoice always got a new number; 567 stayed voided.
  Separately, syncedLock (= !!qb_invoice_id) locked EVERY dollar field whenever a
  QB record existed, so amount/retention couldn't be edited in place either.

FIX 1 — Same-number reissue (handleVoidConfirm, non-pay-app pullback branch):
  Keep the SAME SC row and its qb_invoice_id; reset it to an editable New draft.
  Do NOT set voided_at, do NOT mint a new number, do NOT insert a replacement row.
  (Pay-app pullback path UNCHANGED — still two-row void; its dollars are owned by
  the billing-schedule flow. T&M pullback path UNCHANGED — still delete+recreate.)

FIX 2 — Split the one lock into two (was `syncedLock`):
  • numberLock = !!inv.qb_invoice_id       → freezes the invoice # field (2585).
  • moneyLock  = !!inv.qb_invoice_id && !isNew
        → freezes amount/retention/discount/line-% ONLY while the invoice is still
          live/Sent. A pulled-back invoice is status New → moneyLock false →
          dollars unlock so the correction can be made; the number stays frozen.
  All dollar-input `disabled=` + the handleSaveEdit money-preserve branches now key
  on moneyLock; the invoice-# input + deposit-retention-zero guard key on numberLock.

REOPEN MECHANISM (no code change — existing qb-sync-invoice isUpdate path):
  On resend/save, qb-sync-invoice sees qb_invoice_id set → isUpdate → GETs the
  (voided) QB invoice, takes its SyncToken, POSTs a full sparse:false update with
  fresh Line data. QuickBooks REOPENS the voided invoice with the new lines, SAME
  DocNumber. The SC row's voided_at is null, so qb-sync's "voided → skip" terminal
  gate (index.ts:140) is NOT hit.

UI: new edit-mode banner for the pulled-back (New + synced) state explaining the
  number is kept and the voided QB record reopens on resend.

GOTCHA (not a bug — cost time this session): the edge-function CORS allowlist
  (_shared/cors.ts) trusts ONLY salescommand.app / scmybiz.com (+ PREVIEW_ORIGINS).
  From a *.vercel.app PREVIEW URL every edge-fn call fails with "Failed to send a
  request to the Edge Function," and handleSaveEdit keeps the edit form OPEN on a
  QB-sync failure (by design, for retry) — which reads as "can't save." The SC
  write DID commit each time ("saved in Sales Command"). To exercise ANY edge
  function (send-invoice, qb-sync-invoice, etc.) you must be on scmybiz.com, or pin
  the preview origin into PREVIEW_ORIGINS for a testing window. Preview + prod share
  the one Supabase DB, so a save made on the preview is already in prod data.
