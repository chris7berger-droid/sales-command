     inherits sod_due_minutes/mod_due_hours/eod_required/prt_required (has_column_
     privilege = true for all four). The migration comment's phrasing "No anon
     grant" is therefore imprecise — the columns ARE granted to anon.
   - BUT RLS is ENABLED on tenant_config and there is NO anon policy on the table
     (only authenticated: tenant_config_select USING id=get_user_tenant_id(),
     and tenant_config_update USING id=get_user_tenant_id() AND is_admin_or_manager()).
     No permissive anon policy => anon reads ZERO rows => the 4 columns are
     unreachable by anon. Outcome is correct; the safety comes from RLS, not from
     the (nonexistent) column-grant restriction.
   - fetchFieldThresholds() reads them as the authenticated user with
     .limit(1).maybeSingle() and no manual tenant filter; RLS scopes the select to
     the caller's own tenant row. Safe.
   - HARDENING (not blocking, filed only as this note): if you want the migration's
     stated reasoning to be true by construction, convert anon's tenant_config grant
     from table-level to a column allowlist (REVOKE SELECT on tenant_config FROM anon;
     GRANT SELECT (company_name, logo_url, ... the public-page columns) TO anon).
     Belt-and-suspenders only — RLS already blocks anon today.
