RESET half of B77: password reset now emails a typed 6-digit code instead of a

SESSION SUMMARY
---------------
Picked up B77 (reset/invite email links pre-consumed by ATP SafeLinks). Judged
it a contained auth change — not the full 6-terminal ceremony — so: built the
reset-OTP change, ran one /security-review gate, deployed, merged. The core fix:
`generateLink` already returns a 6-digit `email_otp` alongside the link, so the
reset email now sends the CODE (a scanner can't "click" a number) and the login
screen verifies it with `verifyOtp({type:'recovery'})` then `updateUser`. Security

leaving to fetch the emailed code and coming back; (2) no confirm-password field;
(3) after reset it auto-logged into the app instead of forcing a fresh sign-in.
Reset is now fully verified live. Deferred: the invite half (its own build), the
optional 8-digit toggle, and the ~1-2 min email delivery delay (filed B81).

DECISIONS / CHOICES MADE
------------------------
- No full T6 for this. Judged reset-OTP a contained, well-understood auth change;
  ran ONE gate (/security-review) rather than the 6-terminal protocol. It touches
  live auth, so the security gate was kept, not skipped.
- Ship reset now, defer invite. B77 rolls reset + invite together, but invite is a
  materially bigger surface (its magic link establishes the session that routes to
  WelcomeScreen onboarding — converting needs a new code-entry screen wired into
  App.jsx routing). Shipped the reset half (what actually bit Chris) and left the
  invite half explicitly owned on B77 as a fast-follow, not orphaned.
- Pre-closed security finding #1 rather than defer it. The 6-digit code is a 20-bit
  space; review flagged it SHOULD-FIX (same posture as Supabase's own shipped email-
  OTP login) and cleared it as ship-safe. The recommended fix is bumping OTP length
  to 8 in Supabase Auth — but the frontend hard-capped input at 6, which would have
  silently broken an 8-digit code. Raised the cap to 8 now (safe either way) so the
  toggle is decoupled and can be flipped anytime.
- Match check before code consumption. verifyOtp burns the one-time code, so the
  confirm-password match is validated BEFORE verifyOtp — a typo fails without
  wasting the code.
- Force fresh sign-in after reset. verifyOtp signs the user in, which was dropping
  them straight into the app. Chose to signOut() + reload to /login so a reset
  always ends at a real sign-in with the new password.
- Email delay is not our code. Diagnosed the ~1-2 min code-email delay as recipient-
  side (Microsoft/Outlook ATP scanning), not app latency; filed B81 with the real
  lever (sender-domain reputation / §5c-i) and SMS-OTP as the nuclear option. Chris
  deferred it.
