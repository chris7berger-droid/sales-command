DECISIONS / CHOICES MADE
------------------------------------------------------------
- Rehearsal method: no separate prod-shaped DB exists, so rehearsed by running the
  REAL script with COMMIT -> ROLLBACK against prod (probed first that BEGIN/ROLLBACK
  is honored via the Management API path). Faithful, saves nothing. This is now the
  practical answer to runbook §6.7's open "which rehearsal is realistic" question.
- Mobilizations over de-dup: chose to let multiple old rows attach to one call_log
  (each its own dated jobs row) rather than force one-row-per-job. Matches how live
  prod already stores multi-mobilization jobs, and preserves every date — required
  for the schedule to place jobs.
- PW read is call_log OR jobs (not a data backfill): kept the fix in the read layer
  so it also honors the schedule's own PW checkbox (which writes the jobs row) and
  needs no write to shared master records. prevailing_wage feeds only the schedule's
  own cost rollup; nothing on the Sales/invoicing side reads call_log.prevailing_wage.
- Double-booking glitch PARKED at Chris's direction. Root cause found: the crew
  schedule counts every assignment in the week's date range for double-book
  detection, including stray assignments dated outside a job's own schedule (e.g.
  job 10053 runs Aug 24–Sep 4 but has Jul 27 crew rows). Pre-exists in the Apps
  Script app; a data-logging quirk. NOT fixed this session.
